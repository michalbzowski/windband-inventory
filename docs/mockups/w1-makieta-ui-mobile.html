windband-inventory — makieta widoków · aplikacja mobilna v1

High-fidelity makieta projektowa (design board) implementująca wymagania zamrożone w docs/w1-analiza-biznesowa-2026-10-12.md (R1–R5). Rdzeń: spis z naturą F5 (B7) + baza v1 (B6). Nawigacja jednostronna z WM (B11), role ADMIN/MEMBER z API WM (B8/B10), offline queue (B7/NFR). Ekran 09 jest interaktywny — kliknij OK / BRAK / USZKODZONE i prześledź flow z auto-next.

viewport 360–390 px · zero scroll poziomego tap targets ≥ 44 px pinned bottom bar React + TS SPA (B12) SSO Keycloak realm „windband" (B5) polski UI

IA Architektura informacji — 4 zakładki, role zależne

Wejście wyłącznie z WM (link na dashboardzie bandu / karcie ekwipunku — B11, bez przycisku powrotu w v1). Po SSO: 1 band → od razu Pulpit; ≥2 bandy → ekran wyboru (01). nawigacja dolna stała dla obu ról; różnice zakresu sygnalizowane in-place (button disabled + explain), nigdy ukrywane „w ciszy" — MEMBER musi rozumieć, dlaczego czegoś nie może.

🏠 Pulpit
  • ADMIN: trwa spis → wznów · szybkie akcje (nowa pozycja, rozpocznij spis)
  • MEMBER: podgląd statusów + „trwa spis — dołącz do liczenia"
  • liczniki: dostępne / przypisane / w serwisie / braki
📦 Ekwipunek
  • lista pozycji + filtry: typ / status / magazyn / osoba (B6)
  • szczegóły pozycji → przydział · zwrot · transfer · historia
  • nowa pozycja: wizard 2-krokowy (typ → atrybuty, D1)
✓ Liczenie
  • ADMIN: panel startu spisu (filtry zakresu) · pauza/wznów · zamknięcie
  • MEMBER: dołączenie do trwającego spisu → karty pozycji (F5)
  • offline queue widoczna w tym samym module (localStorage)
👤 Moje
  • własne przydziały + zwrot ze stanem i notką (B6)
  • moje liczenia w spisach (countedBy)
  • status synchronizacji kolejki · wylogowanie

A Wejście i wybór bandu

B Baza ekwipunku (B6) — listy, szczegóły, przydziały, CRUD

Lista z filtrami = główny widok pracy ADMIN-a. Karta pozycji celowo pokazuje numer seryjny i osobę/magazyn — te same dane, które potem zobaczy w liczeniu (spójność rozpoznawalności między modułami).

C Rdzeń v1: spis z naturą (F5, spec zamrożony B7)

Najważniejszy flow aplikacji — liczenie w salce koncertowej, stojąc, często jedną ręką i w słabym zasięgu. Wszystkie decyzje projektowe podporządkowane specowi: 3 duże przyciski, auto-next ~500 ms, live licznik rozbieżności, pause/resume, kolejka offline. Ekrany 09–12 to kolejne stany tego samego widoku.

D Zamknięcie spisu — raport rozbieżności (B9)

E Perspektywa MEMBER — „Moje" (B8)

DS Design tokens — fundament systemu React/TS (B12)

Jeden accent + 3 kolory semantyczne decyzji liczenia. Statusy życia pozycji mają własną skalę, ale NIE współdzielą barw z decision-buttons (OK zielony przycisku ≠ AVAILABLE zielony badge'a — unikamy myślenia „zielony = cokolwiek dobrego").

Makieta koncepcyjna do walidacji z właścicielem aplikacji — nie jest specyfikacją wizualną produkcyjnych komponentów. Po accepted: tokeny + IA + stany 09–13 przenoszone do komponentów React/TS ze stashem w frontend/. Otwarte pytania projektowe: (Q1) czy „Inny stan…" to osobny sheet czy inline-chips, (Q2) auto-next przy BRAK bez notatki: od razu czy z 2 s „cofnij" (rekomendacja: od razu + toast cofnij, by nie łamać specu B7), (Q3) widoczność filtru „Osoba" dla MEMBER-a (rekomendacja: tak, read-only).
